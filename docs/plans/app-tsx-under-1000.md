## 2. 为什么老办法到不了 1000（实测构成）

`App.tsx` = 2957 行；其中 `App()` 函数体 2678 行，顶层语句 **314 条**。

| 性质 | 条数 | 行数 | 能不能靠「抽 hook」搬走 |
|---|---:|---:|---|
| hook-call 解构 glue | 62 | **1238** | ❌ 它是「调用别人」的**接线**，搬到哪都还在 |
| JSX return | 1 | **322** | ⚠️ 能搬到组件，但 props 要原样传，净收益有限 |
| useCallback | 23 | 210 | ✅ |
| hook-call 无解构 | 15 | 153 | ❌ 同 glue |
| useState | 71 | 140 | ⚠️ 可以搬，但搬进 hook 只是换位置 |
| 其它变量 | 50 | 132 | ✅ |
| useEffect | 16 | 101 | ✅（第 14 步已搬了 35 条） |
| useRef | 67 | 80 | ⚠️ 同 useState |
| useMemo | 4 | 28 | ✅ |
| 其它语句 | 5 | 5 | ✅ |
| **合计** | **314** | **2409** | |

**可搬池只剩 210 + 132 + 101 + 28 + 5 ≈ 476 行**（净收益 ~400），抽干也只到 **~2550**。

**关键**：`glue 1238 + glue(无解构) 153 + JSX 322 ≈ 1713 行**是结构性开销** ——
它们不是「待搬的逻辑」，而是「App.tsx 作为组合根，把 258 次 hook 调用的入参一个个摆出来」。
只要 App.tsx 还是组合根，这 1700 行就必然在 App.tsx 里。

所以：**要压到 1000，必须让 App.tsx 不再是组合根。**

## 3. 方案：分层聚合 hook

### 3.1 形状

把 `App()` 里 **258 次 hook 调用 + 穿插的其它语句**，按**源码顺序**切成 4 段连续区间，
每段变成一个「聚合 hook」文件；`App.tsx` 只留：

```tsx
export default function App(props: AppProps) {
  const l1 = useAppLayer1(props);
  const l2 = useAppLayer2({ ...props, ...l1 });
  const l3 = useAppLayer3({ ...props, ...l1, ...l2 });
  const l4 = useAppLayer4({ ...props, ...l1, ...l2, ...l3 });

  const {
    /* 218 个 JSX 要用的名字，按 4 个/行 ≈ 55 行 */
  } = { ...l1, ...l2, ...l3, ...l4 };

  return ( /* 原样保留的 322 行 JSX */ );
}
```

### 3.2 精确测算（`layers3.mjs`，含非 hook 语句）

**4 层 @ 600 行/层（推荐）**

| 层 | 源码区间 | hook 次数 | 其它语句 | 入参名字 | 体 | 返回名字 | **层文件** |
|---|---|---:|---:|---:|---:|---:|---:|
| 层1 | L281-950 | 162 | 14 条/24 行 | 0 | 600 | 335 | **687** |
| 层2 | L951-1602 | 37 | 0 | 125 | 588 | 101 | **648** |
| 层3 | L1604-2274 | 33 | 18 条/66 行 | 200 | 586 | 55 | **652** |
| 层4 | L2276-2633 | 26 | 23 条/47 行 | 193 | 313 | 28 | **371** |

→ `App.tsx` ≈ imports 280 + 4 行调用 + 汇总解构 218 个(55 行) + JSX 322 + 杂项 ≈ **681 行**
→ 5 个文件全部 < 1000，**最大 687，余量 313 行**。

> ⚠️ **前提：`cut.py` 要改一处排版。** 它现在生成
> `  return {\n    a,\n    b,\n…` —— **每个名字一行**，入参解构则是**挤在一行**。
> 按现状排版，层1 会变成 `1 + 600 + 335 + 2 = **938**`（余量只剩 62），
> 而 193 个入参挤成一行会有 ~2500 字符的单行。
> 改成「入参解构与返回都按 4 个/行」后就是上表的数字（层1 687，余量 313）。
> **这是开工第 0 步的一部分**，不是可选项。

**3 层 @ 800（备选，不推荐）**：层1 会到 ~1018 行（`896 体 + 357 返回`）——**直接顶破 1000**。
即使用排版 B，层1 也是 `896 + 90 + 2 = 988`，余量只剩 12 行。
**3 层方案实质不可行**，之前那版测算（919/845/655）是低估了返回对象的行数。

**为什么 4 层**：余量 313 行 vs 12 行。多一个文件的代价远小于顶破 1000 的代价。

### 3.3 为什么这样是安全的

1. **hook 调用顺序完全不变**。层是**连续切片**，层内按原顺序调用，层间按原顺序调用 ⇒
   258 次 hook 的总顺序与今天逐字相同。React 只要求顺序稳定，而 effect 的执行次序、
   ref 的读写次序都依赖这个顺序 —— 保住了。
2. **所有子 hook 签名不变**。搬的只是「谁把入参摆出来」：以前是 `App.tsx`，
   现在是聚合层。`useAppPluginTrust` / `useSessionLifecycle` 等 70 个模块**一个字不改**。
3. **搬运仍是逐字的**。层文件 = 原语句按区间原样剪切 + 一个入参解构 + 一个返回对象。
   沿用 `cut.py`，继续用 `verbatim.py` / `verbatimeff.py` 守住「搬走的代码一个字不改」。
4. **`useState` / `useRef` 的宿主从 App.tsx 变成层 hook**，但调用位置与顺序不变 ⇒
   状态身份、生命周期、重挂载行为都不变。
5. **JSX 留在 App.tsx**（不搬）。322 行留在原地，省掉 218 个 props 的传递与重排风险。

### 3.4 一个必须先建的新校验：hook 顺序等价

这是本方案**唯一的新安全网**，必须在第一次搬之前就建好：

```
hookseq.mjs <file…>       # 抽出这些文件里按序排列的 hook 调用名
```

- 从基线 `App.tsx` 抽出 `App()` 里**按序排列的 hook 名序列**；
- 从改造后的 `App.tsx` + 4 个层文件抽出同样的序列；
- **断言两者逐项相同**。任何一项不同 → 立刻停，说明切片越界或顺序被打乱。

没有这条断言，4 层方案就只能靠「测试全绿」间接判断，而顺序问题未必立刻表现为测试红。

**✅ 这个工具已经写好并验过**（`/tmp/mfsprobe/hookseq.mjs`）：

| 检查 | 结果 |
|---|---|
| 对现状 `App.tsx` 跑出的序列长度 | **258**（与 `hookorder.mjs` 的 258 次一致） |
| 跑两次结果是否一致 | 一致（确定性） |
| 基线序列已存 | `/tmp/base.seq` |

所以「开工第 0 步」只剩两件小事：把基线序列固定进流程、改 `cut.py` 的排版（§3.2）。

## 4. 测试面与风险（已实测）

| 项 | 实测 |
|---|---|
| 读逻辑路径 `src/App.tsx` 的测试文件 | **37** 个 |
| 逻辑路径当前由多少个物理文件拼成 | **70** 个 |
| 「跨行懒匹配」断言总数 | **106** 条 |
| 其中两侧锚点在**同一个**物理文件 | 49 条（重排数组顺序不影响） |
| 其中两侧锚点**跨物理文件** | **2** 条（静态看还是弱锚点噪声，实际更少） |
| 锚点无法静态定位 | 55 条（需靠跑测试发现） |

**结论**：顺序敏感的断言数量可控。处理办法沿用第 4 步的做法 ——
**红了就重指锚点到真正拥有该代码的模块，判据一字不改**，绝不放宽断言。

**`tests/source-map.mjs` 的数组顺序**：**先按「追加」做，别一上来就重排。**

沿用前 14 步的既有做法 —— 把新层文件**追加到数组末尾**：
`["src/App.tsx", …70 个已抽模块…, layer1, layer2, layer3, layer4]`。
理由：这是改动最小、也最可回退的做法；前 14 步每次都只是追加，测试面实际很稳。

若跑测试发现某条懒匹配断言因为「层代码被排到了 App.tsx 之后」而红，
**再**考虑把层插到数组里 `src/App.tsx` 之前（`[layer1..4, src/App.tsx, …]`），
并在数组里写一条注释说明**为什么**要这个顺序 —— 但**判据一字不改**。

> 注：不存在「完美顺序」。`App.tsx` 本身横跨 1-280（imports）+ 层调用 + 2634+
> （JSX），而层持有 281-2633 —— 无论怎么排都有断言可能受影响。
> 所以先追加、红了再调，而不是先设计一个复杂顺序。

## 6. 红线（本方案不得触碰）

沿用 `deep-split-phase3.md` §六，并针对本方案补充：

| 不做 | 原因 |
|---|---|
| **不改 hook 调用顺序** | 顺序决定 effect 执行次序与 ref 读写次序。层必须是**连续**切片。 |
| 不改依赖数组 / 调用顺序 / state 清理顺序 | 同上 |
| 不用「迟绑定 ref」或转发 stub 绕开窗口 | 把编译期问题挪到运行期，测试抓不到 |
| **不压缩格式来凑行数**（把 props 对象写成一行） | ① 达不到 1000（实测 ~1260）；② 会打掉大量行锚定断言；③ 是骗指标不是拆结构 |
| 不搬 JSX return | 322 行留原地，收益不足抵风险 |
| 不放宽任何测试断言 | 红了重指锚点，不改判据 |
| 不改 70 个子 hook 的签名 | 本方案只搬「接线」，不碰它们 |

## 7. 停损条件（任一条命中即停当前步并重划）

1. `hookseq` 序列与基线不一致 —— 说明切片越界。
2. 某层文件超过 1000 行 —— 说明切片大小算错，重新切分。
3. 需要改某个**子 hook** 的签名才能搬动 —— 说明该切片跨越了领域边界。
4. 需要放宽或删除任何测试断言才能全绿 —— 说明顺序真的变了。
5. e2e 出现任何行为差异（10 passed 之外）。

## 9. 需要用户拍板的 3 个决策点

1. **层数**：推荐 **4 层**（最大 687 行，余量 313）。
   3 层**实质不可行** —— 层1 会到 988~1018 行，直接顶破或只剩 12 行余量（§3.2）。
2. **`App.tsx` 的最终形态**：本方案保留 322 行 JSX，`App.tsx` ≈ 700 行。
   若还想更小（≈380 行），需要**额外**把 JSX 搬进 `AppShell` 组件并传 218 个 props ——
   那是另一刀，风险独立，**建议不在本次做**。
3. **层文件的命名**：现在按位置叫 `useAppLayer1..4`。若批准，我会按各层实际内容
   改成有意义的名字（如 `useAppSessionCore` / `useAppWorkspaceCore`），
   但**改名字不改变切片边界**。
