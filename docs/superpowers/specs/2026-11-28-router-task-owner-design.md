# Router 任务负责人化设计

- 日期：2026-11-28
- 状态：已批准（2026-11-28）
- 范围：看板任务 Router 的行为、契约、记忆、恢复与消息策略

## 1. 背景

当前 Router 是事件驱动的调度器：每个事件回合看一份 Situation Brief，选一个工具，写一条消息。它能把活派出去，但承担不了「任务负责人」的职责：

- **停在汇报上**：`turn_settled` 被当成任务收口，而巡检类回合只允许 `router_say` / `router_ask_user` / `router_silent`，Router 即使发现任务没做完也无法继续推进。任务因此经常停在一次 worker 汇报之后。
- **消息重复、细节过载**：每轮至少一条消息；结算回合强制四段式 summary（结论/证据/没做或未验证/下一步），并有 200–400 字、硬上限 800 字的要求。同一结论常在 progress、reply、summary 里出现多次；节点输出被搬进用户消息；文件名、命令、哈希、路径不分场合地出现。
- **没有契约**：完成与否靠系统证据门和临场登记的验收项，Router 没有稳定依据判断「离用户预期还差多少」。
- **没有恢复账本**：服务重启、worker 崩溃、run 孤儿化之后，没有启动对账，任务等用户来催。
- **没有跨任务记忆**：用户的决策和偏好每次都要重说；节点/项目/会话状态也没有可查的归口。

目标是把 Router 从「调度器」变成「任务负责人」：接单、立契约、派活、看护、验收、收口。

## 2. 目标与非目标

### 目标

1. Router 是任务负责人，对任务从接单到收口全程负责。
2. 自动跟踪 worker：worker 汇报、报错、服务重启后都能确认真实状态，并继续或重试。
3. 长任务 30 分钟没有用户可见消息时，主动探针并简报实际进度。
4. 完成时按契约逐条验收；小差距自动补，大差距才问用户。
5. 只有高价值选择交给用户；ask 前后有简短、自然的说明。
6. worker 提问尽量代答，不原样转发。
7. 两层记忆（用户级、项目级），由决策记录自动归纳；用户可查、可改、可删。
8. 接单先澄清（内置 refine，0–2 个高价值问题），再决定怎么派。

### 非目标

- 不替代执行层；不读大块代码和思考，除非确实无法判断在做什么。
- 不做跨任务的优先级、资源调度和排队。
- 不做推送通知；只写任务时间线。
- 不改变 B2 审批边界本身。
- 跨节点记忆同步不在本期；记忆按节点/账户本地生效。

### 反目标

- 每轮强制一条消息、固定四段式 summary、字数硬限制。
- 把节点输出原文搬进用户消息。
- 没有证据就宣告完成。
- Router 自行越过 B2 审批边界。

## 3. 约束

- 事件模型不变：`user_message` / `turn_settled` / `run_settled` / `run_failed` / `completion_blocked` / `startup_reconcile` 等继续作为 Router 回合的触发源。
- 工具面扩展：Router 获得工作区只读文件工具（Read / Grep / Glob）、受限 shell（白名单结构化命令）和专属 Router 文件夹（全局 / 项目两级）的写权限；工作区代码写入仍交给 agent。
- `turn_settled` 当前只允许 say / ask / silent；必须放开继续推进的权限，否则「检查点继续」无法实现。
- Router 只能读工作区文件、跑白名单命令、写专属 Router 文件夹；敏感路径（密钥、`.env`、账户配置、系统单元等）一律拒绝。探针仍优先读转录并过滤大段代码/思考。
- 验收证据来自系统机检、独立复核结论、受限命令结果和转录摘录；Router 自己的文字不算证据。
- 不推送；决策与完成也只写时间线。
- 多节点、共享 worktree、本机重启权限等工程边界沿用仓库现有约定。

## 4. 方案选择

| 维度 | 考虑过的选项 | 选择 | 理由 |
|---|---|---|---|
| 契约承载 | A 提示词约定；B 一等对象 | **B** | 契约要参与派活、看护、验收三处判断，必须是可版本化、可引用的数据，不能只是提示词里的一段话 |
| 验收方式 | A 全自动；B1 机检 + 独立复核 + Router 决策；B2 全部问用户 | **B1（整合版）** | 机器能判的自动判；判断项由独立复核给证据，Router 基于同一份报告决定继续/问/收口；用户保留推翻权。全部问用户会退回「什么都问」 |
| 审批边界 | 更宽 / 更窄 / B2 七类 + 扩展 | **B2** | 删除数据、停服务、花钱、对外发消息、改产品方向、密钥、权限，加不可逆/高成本/跨项目/偏好冲突 |
| 记忆 | A 单层；B 每任务一份；C 只记显式；D1 用户级 + 项目级 | **D1** | 跨任务可复用；项目覆盖用户；实时系统状态不落记忆 |
| 记忆写入 | A 只记显式；B 显式 + 重复纠正；C 每个决策都记 | **记录全量、归纳有门槛** | 决策记录自动落库不靠判断；归纳只提升跨任务仍成立的条目，避免污染 |
| 接单 | A 复用共享 refine；B 内置专属 | **B** | 内置版本可裁剪到 0–2 问、直接产出契约，不受共享 skill 演化的影响 |
| 消息 | A 每轮必发；B 按价值 | **B** | 用户要的是「有情况才说」；沉默也是合法输出 |
| 监督 | A 固定节奏汇报；B 状态变更 / 长期静默两触发 | **B** | 避免「又无进展又有进展」的自相矛盾；只在有变化或长期沉默时打扰 |
| 重试 | A 无限；B 失败一次就问；C 连续 3 次停 | **C** | 自动推进，但有停点；有实质进展重置计数 |
| 恢复 | A 从事件推断；B 显式状态机 | **B** | 重启后需要确定性的对账依据，推断在事件缺失时不可靠 |
| 工具范围 | A 只读 + 受限命令；A+ 加工作区内写；C 全量 shell + 容器 | **A + Router 文件夹写** | 够用于探针和验收，又不开工作区写与 B2 口子；Router 的写只落在自己的记忆/决策文件 |

## 5. 设计

### 5.1 任务契约（一等对象）

契约是任务范围、验收与变更的唯一依据。数据是结构化的，Markdown 只是视图。

| 字段 | 说明 |
|---|---|
| `goal` | 一句话目标 |
| `scope.in` / `scope.out` | 做什么 / 不做什么 |
| `acceptance[]` | 验收项：`text`、`evidence`（machine / verification / user）、`spec`（命令、产物路径或复核口径）、`status` |
| `constraints` | 环境、节点、时间、不许动的东西 |
| `assumptions[]` | Router 先定下、没问用户的假设 |
| `open_questions[]` | 不阻塞开工的待定项 |
| `version` | 每次变更 +1，旧版留档 |
| `provenance` | 每项来源：`user`（关联 decision id）或 `router` |

变更规则：

- **用户敲定的项冻结**：有 ask 记录为证，Router 不能自行修改；要改必须再问。
- **Router 自定的项**（假设、推断的验收方式）可以合理调整，但要告知并留记录。
- 验收项不能静默删除或弱化；删除、弱化必须先问用户。
- 契约进任务卡，用户随时能看、能改；用户改等同于一次用户决策。

### 5.2 接单（内置 refine）

- **触发**：`user_message` 且任务还没有有效契约（首条留言），或用户明显改了目标。续聊、回答上一轮问题、追问细节不走完整 refine，最多一次确认。
- **形态**：内置在 `server/internal/kanban/`，不参与共享 skill；依据现有 refine 裁剪，0–2 个高价值问题。
- **判断**：有重要待办（答案会改变交付或验收、命中 B2、依赖用户偏好且无法推断）→ 用 `router_ask_user` 问；没有 → 写契约、直接开工。
- **产出**：`task_contract` v1，写进任务卡；假设写进 `assumptions`，不假装已确认。
- **与现有规则的关系**：refine 是规则 4 之前的第 0 步，只负责「想清楚要什么」；想清楚后仍按规则 4 选择 workflow / agent / ask。规则 5–9 不动。

### 5.3 状态机与崩溃恢复

状态：

```
intake → contracted → running ↔ waiting_user → accepting → done
                         ↘ paused（用户手动暂停）
```

每次状态转移写一条记录，不从事件反推。

持久化的最小集：

- `contract_version`
- `current_goal` / `current_step`
- `last_dispatch`：`dispatch_id`、目标、时间
- `pending_ask`：问题、选项、提问时间、decision id
- `last_report_at`：探针水位
- `retry_count`

其余（活动、节点产出、历史）从现有 activities / runs 推导，不重复存。

启动对账（`startup_reconcile`）：

- 每个非终态任务跑一次。
- 先核对真实状态：run 是否还活着、节点状态、pending ask 是否已被回答。
- 孤儿 run 标失败；待答问题保留、不重问；已派发但结果未知的先探针，确认没在跑才重派。
- 幂等：每次派发带 `dispatch_id`，重派前查它有没有结果，避免重复副作用。
- **与旧规则的关系**：本设计明确取代「重启后不重放、Router 不自动 cancel/retry」的旧裁定；低层的 unknown 投影与回复结算继续复用。
- **区分崩溃与离线**：节点只是不可达（离线、网络断）时等待并探测，不标失败；只有确认 run 已死（无会话、启动探针判定不可恢复）才标失败并进入重试。

重试：

- 任务级 `consecutive_failures`：一次推进尝试没有带来「新通过的验收项或新验证的产物」就 +1；派发失败、`run_failed`、无新通过的 `completion_blocked`、复核 fail/uncertain 都算。
- 有新验收项通过或新产物验证通过 → 计数清零。
- 连续 3 次就停，汇报并等用户决定；用户手动暂停的任务不自动恢复。
- 与现有 per-Run `repairs_used` 并存：`completion_blocked` 消耗一次 repair，同时按上面的规则计入任务级失败；任一预算先到就先停。
- 失败一次不立即问用户，先按重试预算自动处理。

### 5.4 长看护

- **触发**：30 分钟固定，没有用户可见消息且任务仍在执行。不对长构建/长测试放宽。
- **探针**：读转录，从 `last_report_at` 到现在；优先跳过整段代码块和思考，除非看不懂在做什么。必要时用只读文件工具核对产物是否存在、内容是否对得上。
- **汇报原则**：
  - 只说实际进度：在做什么、到哪了、下一步 / 是否卡住。
  - 不贴文件名、命令、哈希、路径；不复述旧结论；不刷空话。
  - 不设字数；一条消息只讲一件事，讲完就停。
- **渠道**：只写时间线，不推送。
- **水位与心跳**：记 `last_report_at`；有增量讲增量。到 30 分钟仍无增量时，只发一句「还在做 X，暂无新进展」，更新水位后继续做事——这是心跳，不算重复汇报。事件驱动的汇报在窗口内没有变化则沉默。
- 报完继续指挥，不等用户。

### 5.5 消息策略

每轮按价值选一个输出：`silent` / 一条 `progress` / 一条 `summary` / `ask`。`chat` 用于回答和解释。

- 没有变化 → `silent`。
- 有用户必须知道的实质变化 → 一条 `progress` 或 `summary`。
- 有必须拍板的事 → `ask`；必要时同轮一条短说明，不重复结论。
- `summary` 只在真收口时写：完成、失败、停下等决定。`turn_settled` 是检查点，不是收口；契约没满足就继续推进，不写总结。
- 每条消息只写「自上次用户可见消息以来的增量」：不复述目标、不复述旧结论、不搬节点输出。
- 细节分层：默认给结果、影响、风险、要用户做什么；文件名 / 命令只在用户要据此判断或复现时出现；哈希 / PID / inode 留在任务详情，不进消息。
- 取消四段式标签和字数硬限制；保留「一个结算回合只有一条 summary」。
- 30 分钟重复汇报兜底保留，但只作系统兜底，不是表达渠道。

### 5.6 验收与差距

worker 报完成后，Router 逐条对契约：

- `machine` 项：由系统按已落库事实、磁盘产物、受限命令结果求值（node_done、gate_approved、file_exists、命令退出码、测试报告、产物哈希）。
- `verification` 项：由独立复核会话给出 pass / fail / uncertain；它只读工作区、不看转录。
- `user` 项：只有用户能确认的主观项，走 ask，记录为 user decision。

一个契约、一个报告：

- 任务契约在 Run 开始时快照成 `RunContract` 并冻结；当前 Run 只按快照求值，任务级修改下一轮生效。这是「源 + 快照」，不是两份契约。
- 求值器逐项产出 `CompletionItemStatus` + 证据引用；Router 读同一份报告做决定。
- 现有 workflow 的 `completion` 块降为实例化时的模板默认值：任务创建时并入任务契约，之后只有一份。老 workflow 不改也能跑。
- Router 不生产证据：它引用报告；自己跑的检查由系统记录命令结果，算 machine 证据。**没证据 = 未完成**。
- 用户推翻：记录为 user decision，契约项标记 waived，留审计。

处理：

- 全过 → 一条结果总结 + `router_complete_task`；用户随时可以推翻重开。
- 小差距（契约内、能自动补、未超重试预算）→ 直接派活补做，不打扰用户。
- 大差距（要改范围或验收、命中 B2、超出重试预算）→ 停下，用 `ask` 给「继续补 / 按现状收 / 改范围」及各自后果。
- 差距汇报只说四件事：做成了什么、差哪几条、为什么重要、要用户选什么。

### 5.7 Worker 提问

- 先自己查：契约、决策记录 / 记忆、转录、实时系统状态；必要时用只读工具核对产物。
- 能定且在当前范围内 → 直接 `router_answer_waiting_node` 代答，记录 `source=router`。
- 只有以下才升级给用户：命中 B2、要改契约或验收、依赖用户偏好且无法推断、确实信息不足。
- 升级时改写成用户能懂的问题，给 2–4 个选项 + 推荐 + 后果；不原样转发。
- 代答的告知：记入决策记录；下一次自然汇报或总结里带一句「我替你定了 X，因为 Y」，不单独发消息（这是本设计的调用）。

### 5.8 记忆

两层：用户级 + 项目级。项目覆盖用户；同层新覆盖旧，旧条目标注「已被取代」，不删除。

**决策记录（append-only）**

- 记录范围：所有面向用户的 `ask`（问题 / 选项 / 答复）；以及改变契约、范围、验收、方案、或之后会被引用为理由的 Router 自决。日常路由选择、工具选择、重试次数留在现有活动 / 决策日志，不进记忆候选。
- Router 自决先记在任务作用域；只有归纳或用户明确「记住」才提升到项目 / 用户级。
- 每次 `ask` 和上述 Router 自决自动落库，不依赖 Router 自觉。
- 字段：id、时间、任务、作用域（task / project / user）、来源（user / router）、问题、选项、用户选择、理由 / 证据。
- 纠正也追加，不改旧条。
- 任务级随任务归档；project / user 级进入记忆候选。
- ask 记录就是用户意图的证据，契约与记忆条目通过 decision id 关联。

**记忆文档（归纳）**

- 从决策记录归纳出的短条目：内容、source、日期、scope、关联 decision id。
- 归纳触发：任务结束必归纳；同一项目未归纳决策累计到阈值（默认 20，可配）归纳；用户说「记住」立即归纳。
- 冲突：项目覆盖用户；用户敲定项冻结；Router 推断项可被新证据修正，修正时告知。
- 核实：用到时先核实；有活跃 worker 时后台定期核实（默认每日一次，可配），重大变化在下一次汇报里说明。
- 系统状态（节点 / 会话 / 项目在不在）不写入记忆，实时查询。
- 用户可查看、编辑、删除；删除留审计。
- 存放：任务级记录随任务库（节点数据面）；项目级记忆在项目的专属 Router 文件夹（如 `<project>/.mindfs/router/`）；用户级记忆在全局 Router 文件夹（账户级，沿用 MetaDir 约定）。跨节点同步不在本期。
- Router 对专属 Router 文件夹有写权限，仅限普通文件，拒绝符号链接和越界路径；用户敲定的记忆条目，Router 不能删除或覆盖，改动要先问。

### 5.9 审批边界（B2）

命中即先问：

- 删除数据、停止服务、花钱、对外发消息、改产品方向、新建或轮换密钥、修改权限。
- 不可逆、高成本、跨项目。
- 与用户已敲定的偏好冲突。

「不用问了」不能豁免；Router 不得把已做当成既成事实汇报。判断依据是这一轮要做的事，不是它叫什么名字。

**落地层级**：提示词规则保留，但不再是唯一防线。工具层加硬门：

- 白名单内命令（测试、构建、git 只读、ls、rg）直接执行；白名单外一律落审批卡，写明完整命令 / 路径和后果，批准后一次性执行。
- 敏感路径（密钥、`.env`、账户配置、系统单元等）读写都拒绝。
- 写权限只落在专属 Router 文件夹；工作区代码写入仍走 agent。
- HumanGate 仍是 workflow 内的显式暂停点；B2 硬门覆盖 Router 自己发起的动作，两者不互相替代。

### 5.10 规则与工具改动

- 修正提示词中「看不到转录、不能读」的矛盾，工具清单补上 `router_read_session`。
- 规则 4 之前加接单 refine 第 0 步。
- `turn_settled` / `turn_stalled` 等巡检回合放开继续推进的权限（`router_message_agent` / `router_run_workflow`，监管工具按证据可用），否则「检查点继续」无法落地。
- 结算 summary 从「每轮强制四段式」改为「只在收口时写」；删除 200–400 / 800 字限制；保留「一个结算回合一条 summary」。
- 保留 30 分钟重复汇报兜底，作为系统兜底而非表达渠道。
- 新增契约、决策记录、记忆的读写能力；Router 获得工作区只读文件工具、受限 shell 和专属 Router 文件夹写权限；具体工具名与表结构留给实现。
- `DefaultRouterToolPolicy` 从「只允许 Router MCP 工具、deny 一切文件 / Shell」改为「Router MCP + 受限文件 / 命令工具」，并在工具层实现 B2 硬门。

## 6. 成功标准

- `turn_settled` 后任务继续推进，不再停在汇报。
- 重启 / 崩溃后启动对账能自动恢复，或明确停下问人。
- 同一结论不在 progress / reply / summary 中重复；30 分钟内无重复汇报。
- `summary` 只在收口出现；无字数硬限。
- 验收逐条有证据；B2 零越过。
- Router 只能读工作区、跑白名单命令、写专属 Router 文件夹；敏感路径零访问。
- 长任务 30 分钟无消息时主动报实况。
- 用户能在任务卡看到契约、决策记录、记忆，并编辑。

## 8. Builder check 的裁定

1. **验收**：一套任务契约 + Run 快照 + 三类证据提供者（machine / verification / user）+ 一个报告，Router 做决定；不设第二条收口路径。现有 workflow 的 `completion` 块降为实例化模板。
2. **工具范围**：工作区只读 + 白名单受限命令 + 专属 Router 文件夹（全局 / 项目两级）写权限；工作区代码写入仍走 agent。
3. **B2 硬门**：白名单 + 敏感路径拒绝 + 白名单外一次性审批；HumanGate 保留为 workflow 内的显式暂停点。
