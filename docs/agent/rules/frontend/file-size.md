# 文件长度与拆分（长期规则）

- **口径**：物理行数，以 `wc -l` 计。
- **软线**：300 行。超过后应在本次工作中判断职责边界并记录明确拆分安排；后续改动不得把它当作无限期搁置的理由。
- **硬线**：500 行。超过必须在合并前拆分。
- **适用范围**：`web/src/` 与 `web/tests/` 内所有手写 `.ts`、`.tsx` 与 `.mjs` 源文件，
  统一适用，不按路径、内容类型或历史状态区分。构建产物放在输出目录，不作为源码维护。
  **测试文件同样适用**（对齐后端 `file-size.md` 的「含测试」）—— 守卫测试与源码映射表
  会随功能一起长，不纳入就是给它们开一条无人看守的增长通道。
  > 2026-10-16 补：此前本条只写了 `web/src/`，与 `README.md` 声明的范围（`web/src` + `web/tests`）
  > 自相矛盾，导致 `session-window.test.mjs`（787）、`task-panel-unification.test.mjs`（665）、
  > `source-map.mjs`（655）三个超硬线文件长期无人登记。三个文件当天已拆到线下，
  > `web/tests/reviewer-architecture-rules.test.mjs` 的 500 行门禁同步扩到 `web/tests`（含 `.mjs`），
  > 缺口不再靠人工记得。

## 超了怎么拆（判据优先级）

1. 文件里有多个命名 export 时，按职责拆分，每个模块有清楚的职责和入口。
2. 单一 export 但包含多个内部子职责时，按函数与数据的内聚关系拆兄弟模块，原文件只保留编排。
3. 组件文件可将子组件、逻辑、样式和纯函数分别移到合适模块。
4. hook 文件可按子流程拆分，原 hook 只负责组合调用。

执行原则：小批拆分并做类型检查与相关测试，保持行为不变，并遵循既有源码映射测试方式。
